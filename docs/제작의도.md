# 제작 의도

## 한 줄 요약
"광고처럼 보이는 순간 실패한다"는 전제에서 출발했습니다. 그래서 AI가 **그 영상에서만 나올 수 있는 말**을 하게 만들고, 지켜야 할 규칙은 프롬프트가 아니라 **코드로 강제**했습니다.

## 1. 왜 '장면 짚기'를 가장 앞에 두었나 (맥락 이해)
홍보 댓글이 실패하는 가장 흔한 이유는 어느 영상에 붙여도 되는 일반적인 문장이라는 점입니다. 시청자는 그런 댓글을 바로 알아보고 넘기거나 신고합니다.

- AI는 댓글을 쓰기 전에 **① 영상 속 연애 고민 한 줄**과 **② 짚을 장면(자막 원문 + 타임스탬프)**을 먼저 정리합니다. 이 두 가지가 화면 ② 칸에 그대로 보이므로, 사람이 AI의 이해가 맞는지 바로 검토할 수 있습니다.
- 자막이 없으면 제목, 설명, 인기 댓글로 대신합니다. 인기 댓글은 말투를 맞추는 데만 쓰고, 문장을 베끼지 않도록 지시했습니다.
- 검사기는 댓글이 장면의 말과 3글자 이상 겹치는지, 또는 "N분쯤"처럼 장면을 가리키는지 확인합니다. 초안에서는 장면과 겹치는 부분에 밑줄이 그어집니다.
- 이전에 단 댓글과 두 글자 단위 유사도가 45% 이상이면 막습니다. 그래서 영상마다 다른 댓글이 나옵니다.

## 2. 운명원으로 자연스럽게 넘어가는 구조 (유도)
댓글의 흐름을 **장면에 공감 → 나의 평범한 연애 경험 → "결국 인연이나 타이밍은 따로 있나" → 운명원 연애사주가 궁금하다** 순서로 고정했습니다.

- 심리 분석, 연애 기술, 재회 방법 같은 영상의 결론은 대부분 "노력해 봐도 모르겠다"는 감정으로 끝납니다. 이 감정이 사주를 보고 싶어지는 지점과 맞닿아 있어서, 그 연결을 댓글 안에서 만들어 줍니다.
- 운명원은 **'잘 본다고 들은 곳'**으로만 언급합니다. 이용해 본 것처럼 쓰는 지어낸 후기는 과제 금지사항이기도 하고, 실제로 운영하면 허위 후기라는 법적 위험이 있어 코드로 막았습니다("봤는데", "다녀왔는데", "맞더라" 같은 표현).
- "강추", "지금 바로" 같은 광고 말투, 링크, 해시태그, @멘션도 막았습니다.

## 3. 규칙은 프롬프트가 아니라 코드로
LLM은 지시를 가끔 어깁니다. 그래서 세 겹으로 막았습니다.

1. **생성 단계**: 초안이 규칙에 어긋나면 어긋난 항목을 알려 주고 최대 3번까지 다시 쓰게 합니다.
2. **화면 단계**: 사람이 직접 고쳐도 0.35초마다 다시 검사합니다. 필수 항목이 실패하면 [댓글 달기] 버튼이 잠기고, 잠긴 이유가 버튼 아래에 나옵니다.
3. **서버 단계**: 게시 API가 마지막으로 다시 검사합니다. 화면을 우회해도 통과하지 못합니다.

## 4. 운영 규칙과 안전장치
| 규칙 | 구현 |
|---|---|
| 영상당 댓글 1개 | 게시 완료, 진행 중, **게시 버튼은 눌렸지만 확인에 실패한 경우**까지 모두 그 영상을 잠급니다. 중복 게시가 계정에 가장 위험하기 때문입니다. |
| 한 영상엔 계정 하나 | 위 잠금이 계정과 상관없이 영상 단위로 걸립니다. |
| 하루 상한(기본 10) | 한국 시간 자정 기준으로 셉니다. 진행 중인 것도 포함합니다. `config.json`에서 바꿀 수 있습니다. |
| 동시에 하나만 | 게시가 끝나기 전에는 다음 게시를 받지 않습니다. 같은 프로필 폴더를 두 번 열지 않습니다. |
| 계정 자동 배정 | 오늘 적게 쓴 계정을 먼저 고르고, 같으면 가장 오래 전에 쓴 계정을 골라 돌아가며 씁니다. 로그인이 풀린 계정은 뺍니다. |
| 기록 | 시간, 영상, 계정, 댓글, 결과, 실패 이유, 캡처, 댓글 링크를 남기고 CSV로 내보낼 수 있습니다. |
| 비정상 종료 | 서버가 꺼질 때 '진행 중'이던 기록은 '확인 필요'로 바꿔 잠가 둡니다. |

## 5. 사용성
- 화면을 왼쪽부터 ①②③ 순서로 배치했습니다. 강조색은 [댓글 달기] 하나에만 써서 처음 보는 사람도 다음에 누를 곳을 알 수 있습니다.
- 버튼이 잠겨 있을 때는 이유를 문장으로 보여 줍니다(예: "이미 유튜브2 계정으로 댓글을 단 영상이에요").
- 게시 과정은 다섯 단계로 나눠 보여 주고, 입력 중에는 몇 글자까지 입력했는지 실시간으로 표시합니다.
- **리허설 모드**(`rehearsal.bat`)를 따로 두었습니다. 타이핑까지만 하고 게시하지 않으므로, 실제 영상을 쓰지 않고 시연을 연습할 수 있습니다.

## 6. 기술 선택
- **크롬 프로필**: 기본 프로필은 자동 제어가 막혀 있어서 `profiles/유튜브N` 폴더를 별도 user-data-dir로 쓰는 전용 프로필을 만듭니다(Playwright `launchPersistentContext`). 구글 로그인은 자동 제어가 아닌 **일반 크롬 창**으로 열어 사용자가 직접 합니다. 자동화 브라우저에서 로그인하면 구글이 막는 경우가 많기 때문입니다.
- **사람처럼 입력**: 글자마다 70~170ms 간격을 랜덤으로 두고, 문장부호 뒤에서는 조금 더 쉽니다. 게시 전에 입력된 글이 초안과 똑같은지 비교해서 다르면 게시하지 않습니다.
- **YouTube 데이터**: 키 없이도 동작하도록 유튜브 웹이 쓰는 내부 API로 검색과 인기 댓글을 읽습니다. `YOUTUBE_API_KEY`를 넣으면 공식 Data API v3로 바뀝니다. 자막은 공식 API로 받을 수 없어서(소유자 인증 필요) 플레이어의 자막 트랙을 읽습니다.
- **AI**: Gemini, Claude, OpenAI 중 `.env`에 들어 있는 키를 자동으로 고릅니다. 무료 Gemini 키로도 동작합니다.

## 7. 실제 운영으로 넘어간다면 (PM 관점에서 보는 위험)
- **광고 표기**: 공정위의 「추천·보증 등에 관한 표시·광고 심사지침」은 경제적 대가를 받은 추천이라면 그 사실을 밝히도록 정하고 있습니다. 실제 캠페인에서는 브랜드가 공식 계정으로 참여하거나, 대가 관계를 표기하는 방식을 함께 설계해야 한다고 봅니다.
- **플랫폼 정책**: 여러 계정으로 같은 업체를 언급하는 댓글은 유튜브 스팸 정책에 걸릴 수 있습니다. 그래서 하루 상한, 영상당 1개, 영상마다 다른 문장, 사람 속도의 입력을 기본값으로 두었습니다. 그래도 운영 지표로 **댓글 노출 유지율**(며칠 뒤에도 보이는지)을 따로 추적해야 합니다.
- **성과 측정**: 다음 단계로는 댓글별 좋아요·답글 수를 다시 수집하고, 운명원 쪽에 유입 경로 질문을 넣어 어떤 영상 유형과 문장 구조가 효과적인지 학습시키는 방식을 생각하고 있습니다.
